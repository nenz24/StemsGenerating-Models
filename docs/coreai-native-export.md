# Native CoreAI export: verified official route

The official documentation is now accessible from this environment. This
supersedes the earlier blocked-page notes and the user-supplied `.aimodels`
spelling, which we initially followed without verification.

| Artifact | Documented purpose |
| --- | --- |
| `.aimodel` | Portable source model, exported using Core AI PyTorch Extensions. |
| `.aimodelc` | Ahead-of-time compiled variant for one device architecture. |

The reviewed integration and ahead-of-time guides use `.aimodel` and `.aimodelc`.
They do not instruct exporting `.aimodels`. No conclusion about other internal
cache suffixes is needed for this workflow. The rejected `.mlpackage` route and
proposed `.mlmodelc` route are retired.

## Authoritative sources

- [CoreAI integration](https://developer.apple.com/documentation/coreai/integrating-on-device-ai-models-in-your-app-with-core-ai)
- [Ahead-of-time compilation](https://developer.apple.com/documentation/coreai/compiling-core-ai-models-ahead-of-time)
- [Apple coreai-torch quickstart](https://github.com/apple/coreai-torch/blob/main/docs/getting-started/quickstart.ipynb)
- [Apple coreai-torch requirements](https://github.com/apple/coreai-torch/blob/main/pyproject.toml)

The quickstart explicitly exports a decomposed `torch.export.ExportedProgram`
using `TorchConverter.add_exported_program(...).to_coreai()`, then calls
`AIProgram.save_asset(path / "model.aimodel")`. Python 3.11+ and PyTorch 2.8+
are required. No Core ML converter is part of this native export.

## Reproduce the tiny asset

Use a separate environment (Python 3.11+):

```bash
python3 -m venv /tmp/coreai-native-export
/tmp/coreai-native-export/bin/python -m pip install -r requirements-coreai-export.txt
/tmp/coreai-native-export/bin/python scripts/export_coreai_native.py --out /tmp/coreai-native-output
```

The exporter refuses to overwrite an existing `affine.aimodel`. It implements
`y = 2*x + 0.25`, exports a Float32 input/output of shape [1, 4] with names `x`
and `y` in function `main`, and saves a PyTorch reference and package checksums.
No trained weights or ACE-Step downloads are needed for this smoke test.

The prepared `ModelCandidates/affine.aimodel` is a genuine native export from
coreai-torch 0.4.3 / coreai-core 1.0.0b3 / PyTorch 2.8.0+cpu. The exporter produced
`main.mlirb`, `metadata.json`, and `main.hash`. The native hash was generated by
Apple's exporter, not reconstructed or added manually. The separate SHA-256
manifest records file identity and does not replace the native hash.

## iPhone smoke test

The **Uji model native** button loads the bundled portable `.aimodel` through
CoreAI, asks for CPU-only specialization, and compares three inference runs with
the PyTorch reference. Existing folder-resource wiring copies the portable
source for direct loading; this experiment does not claim build-time AOT.
The [user-reported native device run](../reviews/coreai-iphone17pro-native-affine/README.md)
now confirms validation, loading and inference on iPhone: three outputs match
exactly, maximum absolute error 0. Load/specialization was 299.960625 ms, first
inference 117.172042 ms, and the two warm runs averaged 0.7699375 ms. These are
probe timings for this tiny model, not an audio or accelerator benchmark.

## Normal Xcode integration and optional AOT

Apple's integration guide says to add the `.aimodel` to the target's Compile
Sources phase. This standard build integration needs the Metal Toolchain,
installed via Xcode Settings > Components > Other Components, or:

```bash
xcodebuild -downloadComponent MetalToolchain
```

The documented optional ahead-of-time command is:

```bash
xcrun coreai-build compile path/to/affine.aimodel \
  --platform iOS --min-deployment-version 27.0 --output compiled/
```

It produces `affine.<architecture>.aimodelc` variants. The user's device reported
`AIModel.deviceArchitectureName == "h18p"`; select its matching output if present,
not an assumed GPU or phone-name suffix. The same `AIModel(contentsOf:)` API
loads a compiled variant. AOT reduces compilation work but still leaves some
on-device specialization. These Apple CLI commands have not been run on a Mac
in this Linux workspace. The iPhone prototype has no remote inference dependency.
